КАК ЧИТАТЬ ДОКУМЕНТАЦИЮ В КОНТЕКСТЕ ЭТОГО СЕРВЕРА

В исследованном коде используется прямой pywin32/COM: AddNewShell, UpdateObject,
CreateReferenceFromObject. В pycatia те же интерфейсы представлены обёртками
со snake_case-именами: add_new_shell, update_object и т. д.

Не следует механически переносить объект pycatia в прямой COM-вызов. У обёртки
и исходного COM-объекта разные Python-типы. Но и списывать каждую ошибку
конвертации на обёртку нельзя: при неверном порядке аргументов CATIA может
пытаться преобразовать bool или число в объект Reference.

Не смешивать три разных сущности:
  - feature: операция/элемент дерева, например Pad;
  - геометрический подэлемент: конкретная грань или ребро результата;
  - Reference: ссылка CATIA на объект или подэлемент для конкретного API.
Ссылка на весь Pad не становится ссылкой на его ребро только потому, что была
получена через CreateReferenceFromObject.

Проверка после изменения модели для перечисленных инструментов:
  - операция применена в ожидаемом документе и контейнере;
  - создан именно нужный объект;
  - пересчёт завершился успешно;
  - фактический параметр/геометрия прочитаны обратно;
  - ответ не сообщает успех, если результат не проверен;
  - при частичном выполнении явно указано, что осталось в модели.
Имена объектов и номера в Selection не являются постоянными идентификаторами.

===============================================================================
01. catia_shell
===============================================================================

Наблюдение: отказ AddNewShell из-за лишних аргументов.
Место: catia_mcp/tools/part_design.py, _shell, около строки 674.
Уверенность: ОТЧЁТ + КОД + API.

Сейчас передаются четыре аргумента: последний feature, ноль и два одинаковых
значения thickness. Здесь одновременно две проблемы: количество аргументов
и подмена удаляемой грани целым feature.

Правильная форма COM-вызова:
  AddNewShell(face_ref, inner_thickness, outer_thickness)

Требуемое поведение:
1. Получить конкретную удаляемую грань выбранного тела.
2. Создать/получить Reference именно на эту грань.
3. Однозначно определить смысл толщины. Для MVP можно поддерживать оболочку
   внутрь: inner_thickness=t, outer_thickness=0. Это проектное решение адаптера,
   которое должно быть отражено в описании инструмента.
4. Не передавать t с обеих сторон автоматически: это другая геометрия стенки.
5. Убедиться, что целевое тело является текущим рабочим контейнером.
6. Создать Shell, выполнить UpdateObject и проверить фактическую толщину.

Схема входа должна давать способ указать грань. Сейчас faces_to_remove
отклоняется, а без него используется последний feature. Пока выбор грани
не реализован, честный ответ — операция не поддерживается для данной цели.
Удаление одного лишнего аргумента не завершает исправление.

Приёмочный пример:
  Блок 40 x 30 x 20 мм. Удалить верхнюю грань, стенка внутрь 2 мм.
  Наружные размеры остаются 40 x 30 x 20 мм.
  Полость: 36 x 26 x 18 мм; дно и боковые стенки по 2 мм.
  Объём: 24000 - 36*26*18 = 7152 мм³.
  Это расчёт для прямоугольного блока без дополнительных скруглений.

Отрицательные проверки: нет выбранной грани; выбран Pad; толщина чрезмерна;
ссылка принадлежит другой детали. Ни один такой случай не должен давать успех.

API:
https://pycatia.readthedocs.io/en/latest/api/pycatia/part_interfaces/shape_factory.html#pycatia.part_interfaces.shape_factory.ShapeFactory.add_new_shell

03. catia_draft
===============================================================================

Наблюдение: неверное количество параметров CATIA.
Место: part_design.py, _draft, около строки 689.
Уверенность: ОТЧЁТ + КОД + API.

Сейчас метод получает только последний feature, neutral_ref и angle.
Контракт AddNewDraft содержит десять аргументов. В порядке передачи:
  грань уклона; нейтральная опора; режим её распространения;
  разделяющая опора; компоненты X/Y/Z направления вытягивания;
  режим уклона; угол; режим выбора граней.

Недостаточно дописать произвольные нули. Каждый аргумент имеет физический смысл.
Нейтральная опора задаёт неизменяемую геометрию, а направление вытягивания
задаётся вектором. Строка pulling_direction='xy' сейчас фактически выбирает
нейтральную плоскость, поэтому название входа не соответствует реализации.

Предлагаемый минимальный контракт инструмента:
  - одна выбранная боковая грань;
  - явно выбранная нейтральная плоская грань;
  - ненулевой вектор вытягивания;
  - угол в градусах;
  - один документированный режим Draft.
Остальные варианты сначала отклонять как неподдерживаемые.

Режимы CATDraft не угадывать по числам. Использовать именованные значения
из проверенной библиотеки типов/таблицы перечислений. Если для выбранного
режима разделяющая опора не нужна, способ представления пустой ссылки
проверить на установленной CATIA; не предполагать, что None всегда допустим.

Приёмочный тест: прямоугольный блок высотой 20 мм, нейтральная нижняя грань,
уклон одной боковой грани 5 градусов. Смещение верхнего ребра по модулю:
  delta = 20*tan(5*pi/180) = примерно 1.749773 мм.
Проверить знак, неизменность нижнего ребра и отсутствие изменения других
невыбранных граней, кроме геометрически необходимых сопряжений.

API:
https://pycatia.readthedocs.io/en/latest/api/pycatia/part_interfaces/shape_factory.html#pycatia.part_interfaces.shape_factory.ShapeFactory.add_new_draft

04. catia_sketch_arc
===============================================================================

Наблюдение: отказ OpenEdition.CreateArc.
Место: sketcher.py, _draw_arc, около строки 374.
Уверенность: ОТЧЁТ + КОД + API.

Метод создания дуги у Factory2D — CreateCircle с границами углового параметра.
Существующий перевод градусов в радианы полезен; нужно исправить имя вызова:
  CreateCircle(cx, cy, radius, start_rad, end_rad)

Требуемая валидация:
  - открыт эскиз именно текущего документа;
  - координаты, радиус и углы конечны;
  - радиус положителен;
  - выбранная дуга имеет однозначную ориентацию;
  - начало нормализовано в [0, 2*pi), конец строго больше начала;
  - соблюдены пределы углового параметра Factory2D.

Для MVP предлагается положительная дуга против часовой стрелки в локальной
системе эскиза, с размахом строго между 0 и 360 градусами. Полную окружность
можно явно отклонять в этом инструменте, предлагая circle. Это решение
публичного интерфейса, не ограничение всех возможностей CATIA.

Не нормализовать оба угла независимо: запрос 350 -> 10 градусов означает
пересечение нуля. При положительном обходе его конец должен стать 370 градусов,
а не остаться меньше начала. Равные углы требуют явного определения семантики.

Тест A: центр (0,0), R=10 мм, 0 -> 90 градусов.
Начало (10,0), конец (0,10), длина 5*pi = 15.707963 мм.
Тест B: 350 -> 10, ожидаемый размах 20 градусов.
Тест C: отрицательный радиус и NaN отклоняются до COM.

После создания сохранить объект дуги для readback, закрыть эскиз при
завершении сценария и проверить пересчёт. Наличие объекта в GeometricElements
ещё не доказывает пригодность всего эскиза для последующего solid feature.

API:
https://pycatia.readthedocs.io/en/latest/api/pycatia/sketcher_interfaces/factory_2D.html#pycatia.sketcher_interfaces.factory_2D.Factory2D.create_circle

05. catia_measure_distance
===============================================================================

Наблюдение: CATIA.Application.GetWorkbench.
Место: measurement.py, _measure_distance, около строки 134.
Уверенность: неверный получатель GetWorkbench подтверждён КОД + API.

Правильная цепочка:
  документ -> GetWorkbench('SPAWorkbench') -> GetMeasurable(reference1)
  -> GetMinimumDistance(reference2).
GetWorkbench должен вызываться у документа, а не у Application.

После этой правки остаётся проблема поиска. Сейчас Selection.Search ищет
имя по всему документу и берёт первый найденный объект. При одинаковых именах
можно молча измерить другую геометрию. Нужно требовать единственное совпадение
либо точный контекст: документ, контейнер, выбранный объект.

Не обещать измерение произвольных Body/HybridBody этой цепочкой: у Measurable
есть ограничения на измерение расстояния между контейнерами. Поддерживаемые
конкретные геометрические типы следует перечислить и проверить.

Единицы длины нельзя вывести из единиц Volume/Area: разные группы Automation
могут иметь разные соглашения. Текущая функция просто подписывает сырое число
как мм. До фиксации коэффициента преобразования выполнить калибровку на двух
точках с известным расстоянием, сохранить raw_value и ожидаемые миллиметры.
Не добавлять автоматически множитель 1000 только из предположения «SPA = SI».

Приёмка:
  A=(0,0,0), B=(30,40,0) мм: ответ 50 мм.
  Параллельные плоские поверхности с зазором 12 мм: ответ 12 мм.
  Пересекающиеся поддерживаемые поверхности: минимум 0.
  Два объекта с одинаковым именем: ошибка неоднозначности, не первый результат.

Возвращать minimum_distance, unit, идентичности целей и систему координат.
Это минимальное геометрическое расстояние, не расстояние между центрами и
не signed penetration depth. Восстанавливать пользовательское выделение,
если внутренний поиск его меняет, либо документировать побочный эффект.

API:
https://pycatia.readthedocs.io/en/latest/api/pycatia/in_interfaces/document.html#pycatia.in_interfaces.document.Document.get_workbench
https://pycatia.readthedocs.io/en/latest/api/pycatia/space_analyses_interfaces/measurable.html#pycatia.space_analyses_interfaces.measurable.Measurable.get_minimum_distance

06. catia_get_inertia
===============================================================================

Наблюдение: отказ на Application.GetWorkbench.
Место: measurement.py, _get_inertia, около строки 162.
Уверенность: несколько независимых проблем подтверждены КОД + API.

В текущем коде:
  - GetWorkbench вызывается у неправильного объекта;
  - Measurable.Volume сразу записывается в volume_mm3;
  - Measurable.Area сразу записывается в area_mm2;
  - затем из ошибочно подписанного объёма вычисляется масса;
  - вызывается measurable.GetInertia, не документированный у Measurable;
  - исключения отдельных измерений подавляются, возможен успешный пустой JSON;
  - описание обещает свойства детали, а измеряется только MainBody.

Объём Measurable документирован в м³, площадь — в м². Следовательно:
  volume_mm3 = volume_m3 * 1e9
  volume_cm3 = volume_m3 * 1e6
  area_mm2   = area_m2 * 1e6
  area_cm2   = area_m2 * 1e4
  mass_kg   = density_kg_m3 * volume_m3
Массу нужно считать из исходного значения полной точности, до округления.

Объект для массовых характеристик — Inertia, получаемый через
Product.GetTechnologicalObject('Inertia'). Его методы включают
GetInertiaMatrix и GetCOGPosition; это отдельный интерфейс от Measurable.
Получение выходных COM-массивов проверить отдельно: обычный Python list
не гарантирует изменение на месте через конкретную pywin32-обёртку.

Контракт результата должен однозначно задавать:
  - scope: вся деталь, выбранное тело или выбранный продукт;
  - использованную плотность и её источник;
  - mass в кг, volume в м³/мм³, area в м²/мм²;
  - центр масс и его систему координат;
  - матрицу инерции, единицы и точку приведения;
  - unavailable_fields с причиной, если поддерживается частичный результат.

Нельзя смешать объём MainBody и инерцию всего продукта. При нескольких телах
нужно либо вычислять всё для одного scope, либо явно отклонять неподдерживаемый
вариант. Плотность, переданная пользователем, должна быть конечной и >0.
При материале с неоднородной плотностью формула m=rho*V с одним rho уже не
описывает исходную модель; такой override должен быть явным.

Не трактовать служебные значения Inertia.Density как надёжную физическую
плотность материала. Чтение 1 может означать default, -1 — неоднородность.
Не выдавать вычисленную с default массу за подтверждённую массу материала.

Физическая размерность массовой инерции — кг*м². В справочном тексте Inertia
встречается неудачная запись единиц; её нельзя копировать как кг²*м².
Проверить также точку приведения возвращаемой матрицы на переносимом тестовом
теле. Если нужна смена точки, применять теорему Штейнера, а не менять подпись.

Приёмочный тест: однородный блок 40 x 30 x 20 мм, rho=1000 кг/м³.
  V = 24000 мм³ = 24 см³ = 2.4e-5 м³.
  A = 5200 мм² = 0.0052 м².
  m = 0.024 кг.
  Центроид для угла блока в начале координат: (20,15,10) мм.
  Матрица относительно центроида, оси параллельны рёбрам:
    Ixx = m*(0.03²+0.02²)/12 = 2.6e-6 кг*м²;
    Iyy = m*(0.04²+0.02²)/12 = 4.0e-6 кг*м²;
    Izz = m*(0.04²+0.03²)/12 = 5.0e-6 кг*м²;
    внедиагональные члены около нуля.
  Для матрицы относительно начала координат значения будут другими.

Повторить после переноса и поворота блока: масса и объём неизменны, центр масс
меняется, матрица в глобальных осях преобразуется как R*I*R^T для той же точки.
Округление до четырёх десятичных знаков уничтожает эти малые моменты инерции;
хранить полную числовую точность, форматировать только отображение.

API:
https://pycatia.readthedocs.io/en/latest/api/pycatia/space_analyses_interfaces/measurable.html
https://pycatia.readthedocs.io/en/latest/api/pycatia/space_analyses_interfaces/inertia.html
https://pycatia.readthedocs.io/en/latest/api/pycatia/product_structure_interfaces/product.html#pycatia.product_structure_interfaces.product.Product.get_technological_object

07. catia_get_bounding_box
===============================================================================

Наблюдение: отказ Application.GetWorkbench.
Место: measurement.py, _get_bounding_box, около строки 216.
Уверенность: первый дефект подтверждён; второй виден при сверке интерфейса.

После GetWorkbench текущий код вызывает Measurable.GetBoundingBox. Такой метод
не найден в проверенном документированном интерфейсе Measurable pycatia.
Поэтому исправление только получателя GetWorkbench недостаточно. Не нужно
заменять его на другое предполагаемое имя без проверки реального интерфейса.

Сначала определить обещаемую величину:
  AABB — минимальные и максимальные координаты вдоль заданных X/Y/Z;
  OBB — ориентированный ограничивающий параллелепипед.
Для данного инструмента разумный MVP — AABB в системе детали, единицы мм.

Математическое определение для всей выбранной геометрии G:
  xmin=min{x : (x,y,z) принадлежит G}; xmax=max{x : (x,y,z) принадлежит G}.
  Аналогично для y и z.
  размеры = (xmax-xmin, ymax-ymin, zmax-zmin).
Измерить только вершины недостаточно: у сферы или криволинейной грани крайняя
координата может находиться внутри кривой/поверхности.

Возможный путь реализации: геометрические экстремумы в шести направлениях
с использованием HybridShapeFactory/HybridShapeExtremum. Это предложение,
а не уже проверенная универсальная замена GetBoundingBox.
Потребуется подтвердить допустимые опоры, охват всех граней целевого тела,
извлечение координаты и случаи, когда экстремум является ребром/гранью,
а не единственной точкой. Дополнительные направления могут устранять
неоднозначность точки без изменения искомой крайней координаты.

Если алгоритм создаёт временную геометрию, measurement перестаёт быть чисто
читающей операцией. Реализовать вычисление на временной копии либо явно
контролируемое восстановление модели. Удаление временного элемента само
по себе не гарантирует восстановления флага Saved, Undo и InWorkObject.
Альтернатива — приближённые границы по тесселяции, но тогда обязательно
возвращать approximate=true и известную точность/ограничения метода.

  Блок с углами (10,20,30) и (50,50,50): размеры (40,30,20).
  Сфера R=10 в центре (5,-2,7): min=(-5,-12,-3), max=(15,8,17).
  Блок 40 x 30 x 20, поворот 45 градусов вокруг Z:

27. catia_move_component
===============================================================================

Наблюдение: сбой поиска компонента в неправильном контексте.
Место: assembly.py, _move_component, около строки 288.
Уверенность: живой тест преобразования отсутствует; риск раскладки матрицы

CATIA Position хранит 12 чисел: последовательно вектор оси X, оси Y, оси Z,
затем координаты начала. Если R преобразует локальные координаты в родительские,
его столбцы — эти оси. Упаковка:
  [R00,R10,R20, R01,R11,R21, R02,R12,R22, tx,ty,tz].

Текущий код вычисляет произведение для расположения элементов, похожего
на построчную раскладку. Для исходной identity и положительного поворота Z
это приводит к транспонированному размещению вращения относительно раскладки

Нужно определить три решения публичного интерфейса:
  1. tx/ty/tz и rx/ry/rz — абсолютная поза или приращение?
  2. приращение задано в системе родителя или самого компонента?
  3. вращение идёт вокруг собственного начала или начала родителя?
Без этого одинаковые числа могут законно давать разные положения.

Предлагаемый MVP: приращение перевода в системе родителя; поворот вокруг
собственного начала компонента; оси поворота выражены в системе родителя;
порядок R_delta=Rz*Ry*Rx. Тогда:
  R_new = R_delta * R_old
  t_new = t_old + delta_t
Это именно выбранная семантика инструмента. Поворот вокруг начала родителя
потребовал бы также повернуть t_old.

Реализация должна явно распаковать оси в матрицу, вычислить произведение,
упаковать обратно, вызвать SetComponents, обновить и перечитать Position.
Проверить R^T*R приблизительно равно identity и det(R) приблизительно +1.
Не считать все нули в выходном Python list корректной позой: это может
означать, что GetComponents не заполнил массив из-за COM marshalling.

Компонент под действием Fix/assembly constraints может не сохранять
запрошенную позу после Update. Поэтому отсутствие исключения SetComponents
не является успехом. Нужен readback после решения сборки и сообщение
о конфликте, если фактическая поза отличается.

  - вложенная подсборка с отличной от глобальной системой родителя;
  - зафиксированный компонент: нет ложного сообщения об успешном перемещении.

Этап 1. Не допускать ложных результатов.
  catia_add_component: проверка фактического добавления.
  catia_get_inertia: единицы, поддерживаемый интерфейс и отсутствие пустого успеха.
  catia_get_bounding_box: заменить недоказанный API-вызов проверенным алгоритмом
  либо явно оставить функцию неподдерживаемой до его реализации.
  Три GSD-инструмента: честный результат cleanup после update failure.

Этап 2. Устранить прямые несоответствия контрактам API.
  Arc; Shell; Thickness; Draft; оба Pattern; Hole.
  Chamfer: режим, распространение и целевой объект.
  Fillet: целевое ребро.
  Shaft/Groove: явная работа с объектом параметра угла.

Этап 3. Обеспечить правильный контекст и адресацию.
  Надёжно различать PartDocument и ProductDocument.
  Разрешать выбранные грани/рёбра и сборочные опоры без поиска первого совпадения.
  Согласовать контракты list_edges, get_selection, create_sketch и list_features.
  Поддержать GSD-типы в update_selected_feature с проверкой владельца.

Этап 4. Проверить сборочные операции на настоящей тестовой сборке.
  add_new_part; Fix; Coincidence; Offset; Angle; Move.
  Обязательно две вставки одной и той же детали и одна вложенная подсборка.

Этап 5. Проверить геометрические гипотезы на независимых простых моделях.
  Shaft; Groove; Mirror; CloseSurface; GSD Revolve; GSD Trim.
  У каждого теста должна быть собственная известная исходная модель.
  Последовательный запуск всех инструментов на одной случайной детали
  смешивает ошибки: failed feature или изменённое InWorkObject может повлиять
  на все следующие команды.

Два уровня проверки:

1. Offline-проверка адаптера.
   Проверить число/порядок аргументов, enum mapping, валидацию входа, преобразование
   единиц, упаковку матрицы, проверку результата и обработку частичных ошибок.
   Mock, принимающий произвольные *args, не проверяет сигнатуру COM-метода.
   Проверка собственной строки «created» не доказывает создание геометрии.

2. Live-проверка на Windows с CATIA.
   Выполнить предложенные выше геометрические примеры через исправленные MCP tools.
   Сохранить вход, фактический результат и измеряемые postconditions.
   При возможности сравнить со штатным UI измерения CATIA и аналитическими
   величинами. Не использовать только другой ещё непроверенный MCP-инструмент
   как единственный источник истины.

Рекомендуемый допуск для размеров простых тестов: заранее выбранный eps_len,
например 1e-3 мм, если он не строже точности используемого измерения/модели.
Для объёма, массы и инерции выбирать отдельные размерные/относительные допуски.
Не применять один абсолютный tolerance ко всем величинам разных единиц.

Минимальная запись для каждого live-испытания:
  tool_name;
  версия/ревизия реально запущенного сервера;
  версия CATIA;
  document identity и тип;
  начальный Body/Geometrical Set/Product context;
  точный входной JSON;
  разрешённые COM-типы целей;
  стадия отказа либо успешное завершение;
  HRESULT/excepinfo при ошибке;
  созданный объект и его фактические параметры;
  update/constraint status;
  независимые измерения и допуски;
  остаточные изменения после ошибки.

Инструмент считается исправленным только в явно проверенном диапазоне:
например «одно выбранное ребро, постоянный радиус, CATPart», а не
«любой Fillet при любых входах». Поддержка остальных режимов расширяется
отдельными геометрическими примерами.

Этот документ содержит план исправления и воспроизводимые критерии проверки.
Ни один приведённый live-сценарий не объявляется уже пройденным.
