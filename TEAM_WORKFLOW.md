# Несколько файлов и агентов для CATIA

Реализовано локально; опубликованная версия может отличаться. Никакой отдельный
платный AI API не используется: агентами управляет установленный Codex/Claude.

## Что взяли из Cursor

В Cursor агент использует общий контекст, поиск и инструменты редактирования;
работа с несколькими файлами сама по себе не требует нескольких агентов.
Для независимых задач используются подагенты, а Git worktrees изолируют правки
отдельных исполнителей. Источники: [Agent](https://cursor.com/docs/agent/overview),
[Search](https://cursor.com/docs/agent/tools/search),
[Worktrees](https://cursor.com/docs/configuration/worktrees).

Для CAD переносим распределение задач и сбор результатов. Git worktree не
изолирует активный документ живой CATIA, её Sketch и COM-состояние. Поэтому:

```text
5 входных файлов
  ├─ worker file_001: свои страницы, размеры, вопросы, план
  ├─ worker file_002: свои страницы, размеры, вопросы, план
  ├─ worker file_003: свои страницы, размеры, вопросы, план
  ├─ worker file_004: свои страницы, размеры, вопросы, план
  └─ worker file_005: свои страницы, размеры, вопросы, план
       ↓ все отчёты готовы
  planner: объединяет детали, виды, интерфейсы и зависимости
       ↓
  reviewer: проверяет размеры, ограничения, риски и критерии результата
       ↓
  coordinator: выполняет через MCP → Update → измеряет → следующая операция
       ↓
  verifier: проверяет переданные модельные данные против общего плана
```

Пять файлов могут оказаться пятью деталями или пятью листами одной детали.
Это выясняется до построения; невидимые размеры не угадываются.
Планирование параллельное, команды в одну CATIA — последовательные.
Остальные документы остаются открытыми. Это не пять CATIA-процессов.

Для сборки integration-planner возвращает полный граф сопряжений: пара деталей,
точные опоры/способ их получения, тип связи, orientation/side/offset, ожидаемая
подвижность, порядок вызовов и контрольные точки. Он использует снимок
`catia_assembly_spatial_context`, предоставленный координатором, и не выдумывает
handles/revision. Координатор выполняет весь разрешённый этап без повторных
«продолжать?», проверяет каждый результат и обновляет ссылки между записями.
См. [Assembly workflow](ASSEMBLY_DRAWING.md). Больше команд не означает больше
ограничений: не добавлять избыточные связи и не блокировать нужное вращение.

## Запуск на Windows

После переноса текущей локальной версии и обычного `INSTALL.cmd`:

1. Открой CATIA. Закрой другие CAD-writing клиенты.
2. Запусти `START_AI.cmd`, выбери Codex или Claude, затем режим **3 — Multiple files + parallel planning team**.
3. В одном диалоге выбери несколько файлов через Ctrl/Shift.
4. После проверки инструментов дай задание, например:
   «Разбери эти пять файлов параллельно. Первые четыре относятся к деталям,
   пятый — сборочный. Сначала сверь сопряжения и недостающие размеры, затем
   создай новые несохранённые детали и сборку. Fix и AutoConstraint запрещены».

Без диалога (из папки проекта):

```powershell
.\START_AI.cmd --client codex --mode team --drawing "C:\Drawings\part-a.pdf" --drawing "C:\Drawings\part-b.pdf" --drawing "C:\Drawings\assembly.png"
```

Допускается 1–20 файлов, до 50 MB на файл, до 12 страниц одного PDF и до
60 растровых страниц на пакет. PDF/PNG/JPEG читаются визуально. CATPart,
CATProduct и CATDrawing сохраняются как входные ссылки: это не парсер CAD.
Их содержимое читает главный агент через MCP после согласованного открытия
нужного оригинала. Он передаёт снимок контекста соответствующему worker.
HEIC сначала экспортируй в PNG/JPEG. Увеличенный фрагмент нужен, если размер
не читается на подготовленной странице.

Главный чат получает не больше пяти обзорных изображений, чтобы не заполнить
его всеми страницами. Это только обзор. Каждый worker обязан открыть ВСЕ
назначенные страницы по путям из manifest, а не предполагать наследование вложений.
Если клиент не умеет передать/прочитать изображение в подагенте, нужно сообщить
об этом; нельзя выдавать чтение имени файла за разбор чертежа.

Режимы **Chat** и **One drawing** в `START_AI.cmd` остаются одиночными.
Автоматический Astra→Luna handoff не совмещается с `--team`.
Команда не выбирает за пользователя платную модель: настройки моделей наследуются
от текущего клиента. Параллельные агенты расходуют дополнительные токены.

## Общий контекст и независимые отчёты

Пакет хранится локально в `.local/cad-team/bundle-.../`:

- `manifest.json`: ID файлов, исходные пути, SHA-256, страницы и зависимости задач.
- `inputs/`: копии входных файлов для согласованного анализа; оригиналы не меняются.
- `pages/`: страницы чертежей, разложенные по ID; одинаковые имена не конфликтуют.
- `tasks/file_001.json` и другие: отдельный ответственный, ревизия, состояние и отчёт.
- `tasks/integrate.json`, `tasks/review.json`: последовательные зависимые стадии.
- `reports/`: файлы ответов, каждому worker выделен собственный путь.

Главный агент сначала читает `status`, затем получает `packet` на каждую задачу
и выдаёт независимые задания. Один worker владеет только своим task ID.
После claim нужно заново получить packet: ревизия и owner уже изменились.
Worker пишет ответ в `owned_report_path`, затем вызывает submit. Файлы
`tasks/*.json` меняются только через CLI, а не прямыми редакциями нескольких агентов.
Команды ниже для агента, пользователю не требуется вводить их вручную:

```powershell
.\.venv\Scripts\python.exe scripts\cad_team.py status "C:\Project\.local\cad-team\bundle-123\manifest.json"
.\.venv\Scripts\python.exe scripts\cad_team.py packet "C:\Project\.local\cad-team\bundle-123\manifest.json" --task file_001
.\.venv\Scripts\python.exe scripts\cad_team.py claim "C:\Project\.local\cad-team\bundle-123\manifest.json" --task file_001 --owner reader_1 --expected-revision 0
.\.venv\Scripts\python.exe scripts\cad_team.py submit "C:\Project\.local\cad-team\bundle-123\manifest.json" --task file_001 --owner reader_1 --expected-revision 1 --report "C:\Project\.local\report-1.json"
```

Формат отчёта (содержимое заполняет worker по своему заданию):

```json
{
  "summary": "На листе одна втулка; наружный диаметр 30 mm указан на виде спереди.",
  "plan": "После уточнения длины: профиль с совпадениями и размерными ограничениями, затем Shaft вокруг construction axis. Не использовать Fix.",
  "checks": ["Проверить наружный диаметр 30 mm через геометрию/параметры"],
  "questions": ["Какова длина втулки? На листе она не указана."],
  "ready": false
}
```

`ready=true` требует отсутствие вопросов и наличие проверок. Это готовность
плана, а не разрешение пользователя и не доказательство построения.
Главный агент собирает вопросы в одно сообщение. Уточнения/живой контекст
передаются через `reset --context <JSON>` с актуальной ревизией задачи; старый
worker после reset уже не сможет отправить результат с прежней ревизией.
Изменения исходников требуют нового пакета. Изменение отчёта инвалидирует
зависимые планы; их надо явно сбросить и пересмотреть. Команды не отменяют
уже выполненные CAD-операции и не являются механизмом Undo.

## Единый передатчик плана (catia_plan_compile / catia_plan_step)

Все агенты выдают параметры в одном формате, а не свободным текстом:

```json
{
  "title": "Пластина 80x50x8 с отверстием",
  "steps": [
    {"id": "sk", "tool": "catia_create_sketch", "args": {"plane": "xy"}},
    {"id": "pad", "tool": "catia_pad", "args": {"height": 8, "sketch_handle": {"$ref": "sk.handle"}}},
    {"id": "vol", "tool": "catia_get_inertia",
     "checks": [{"path": "data.volume_mm3", "op": "approx", "value": 32000, "tolerance": 1}]}
  ]
}
```

- `args` — обычные параметры целевого инструмента; `$ref` ссылается только на
  более ранний шаг (`шаг.путь`, индексы списков числом, `as` задаёт тип).
  Если шаг записи создал ровно один объект, он доступен как `шаг.handle`,
  иначе — `шаг.created_handles.N`.
- `document_id`, `expected_revision`, `request_id` в план не пишутся: request_id
  выводится из plan_id и id шага, ревизию передаёт координатор в `catia_plan_step`.
- `catia_plan_compile` проверяет весь план по тем же схемам и политикам, что и
  сервер, без CATIA. Fix/AutoConstraint, UI и скриншоты отклоняются;
  save/close/export — только с `allow_outputs=true` по явной просьбе пользователя.
- `catia_plan_step` выполняет ровно один следующий шаг, проверяет его `checks` и
  останавливает план при первой ошибке. Повторный вызов завершённого шага не
  выполняет его снова. После остановки — осмотр модели и исправленный план
  (или `attempt`+1). Это не пакетный скрипт и не откат.
- Worker может приложить такой план в поле `program` своего отчёта; `submit`
  отклонит отчёт, если программа не компилируется. Проверка вручную:
  `.\.venv\Scripts\python.exe scripts\cad_team.py compile plan.json`.
  Компиляция подтверждает только параметры и порядок, не геометрию.

## Исполнение в нескольких открытых документах

`catia_get_workspace_state` показывает открытые документы и точные session IDs
без переключения. Главный агент сопоставляет их с файлами плана. Для перехода
использует `catia_activate_document` с ID исходного/целевого документа,
актуальной ревизией источника и новым request_id. До перехода нужно закрыть
Sketch. После него обязательно перечитать `catia_get_model_state` и selection:
старый контекст нельзя использовать для записи в другой документ.

Подагенты не вызывают даже inspection MCP: они работают с пакетами данных,
полученными от координатора. Отдельный `cad_executor` не нужен для записи:
главный агент уже обладает полным MCP. По текущей
[документации Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents)
`mcp_servers` и `sandbox_mode` в role TOML не переопределяют родительскую
конфигурацию. Поэтому это правило распределения работы, а не граница безопасности
между агентами. Для Claude Code те же роли лежат в `.claude/agents/*.md`
(список `tools` без MCP, Bash и Agent); обычный подагент Claude MCP наследует.
Лаунчер Claude, как и Codex, одобряет вызовы `catia-v5` на сессию и разрешает
подагентов только в режиме Team. Одновременно запускается только один клиент, пишущий в CATIA.

В случае ошибки/timeout общий исполнитель останавливается и выясняет состояние.
Никакого автоматического повтора через другой транспорт, сохранения или отката.
Fix/AutoConstraint и UI-ввод остаются заблокированы; снимки экрана доступны.

## Что ещё нужно проверить на Windows

- Реальное создание пяти подагентских задач в выбранной версии Codex/Claude,
  доступ каждой к своим изображениям и полный проход integrate→review.
- Пять открытых тестовых документов: правильный каталог, переключение по ID,
  запрет переключения во время Sketch и повторное чтение перед записью.
- Вручную открытый, не принятый сервером Sketch: COM не даёт здесь подтверждённого
  универсального индикатора; координатор должен уточнить/завершить эту сессию.
- Построение новых несохранённых тестовых деталей по согласованным размерам,
  сборка/чертёж и проверка результата. Mocks не подтверждают геометрию CATIA.

Локальные проверки пакета/очереди не запускают AI-модели и не обращаются к COM.
Нет нового графического приложения со вкладками как у Cursor: работа видна
в чатах подагентов, локальных отчётах и обновляющихся документах CATIA.
